## 13.1 代码格式（Prettier）

根目录新增 `.prettierrc.json`，与现有代码风格一致：

| 选项                   | 取值          | 说明                               |
| ---------------------- | ------------- | ---------------------------------- |
| `semi`                 | `true`        | 语句末尾保留分号                   |
| `singleQuote`          | `false`       | 使用**双引号**（现有代码即双引号） |
| `tabWidth` / `useTabs` | `2` / `false` | 2 空格缩进                         |
| `printWidth`           | `100`         | 单行 100 列                        |
| `trailingComma`        | `"all"`       | 多行结构补尾逗号                   |
| `endOfLine`            | `"lf"`        | 统一 LF（避免 Windows CRLF 混入）  |

`.prettierignore` 排除：`node_modules`、`dist`、`build`、`.wrangler`、`.turbo`、
`data/`、`*.sql`（迁移是手写 DDL，**不应被格式化**）、`package-lock.json`。

**建议命令**（当前未在根 `package.json` 增加 `format` script，避免与其他并行改动冲突）：

```bash
npx prettier --write .    # 格式化
npx prettier --check .    # 仅校验（CI 可用）
```

> ⚠️ 本次**未实际运行** `prettier --write .`，以免重写大量文件与并行工作冲突。
> 首次全量格式化建议在独立提交中完成，并单独评审 diff。

## 13.2 本地环境变量与 secret 注入

`apps/api/.dev.vars.example` 列出本地开发所需绑定（字段名取自 `apps/api/src/env.ts` 的 `Env`）：

 - `JWT_SECRET`、`AGENT_TOKEN_PEPPER`、`PHONE_ENC_KEY`、`PHONE_HASH_PEPPER`（必填 secret）
 - `ENVIRONMENT`（`development` / `staging` / `production`）——⚠️ **只用于自报与 Cookie `Secure` 判定，不得用来开关任何调试后门**（见 §13.7）
 - `DEMO_FIXED_SMS_CODE`（演示固定验证码白名单；逗号分隔手机号，`*` = 全部放行，**空 = 全部不放行**）
 - `AGENT_REQUIRE_SIGNATURE`（可选，默认关闭）

值一律是**明显的占位符**（如 `dev-insecure-secret-change-in-production`），不是真实密钥。

使用方式：

1. `cp apps/api/.dev.vars.example apps/api/.dev.vars` 后替换为本地随机值；
2. `.dev.vars` 已被根 `.gitignore` 忽略（`.gitignore` 第 17 行，注释「环境变量（只提交 .dev.vars.example）」），**绝不提交**；
3. 生产不写 `.dev.vars`，改用 `wrangler secret put <NAME> --config apps/api/wrangler.jsonc` 注入
   （见 `docs/09-认证权限与部署.md` §10）。

| ----------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------- | --------------------------- |
| `apps/api`        | 有（`apps/api/wrangler.jsonc`，worker 名 `dshop-api`）              | `wrangler deploy --config wrangler.jsonc`（原有）+ `deploy:dry`            | ✅ **已真实部署**    | `https://api.eshop.eu.cc`   |
| `apps/storefront` | 有（`apps/storefront/wrangler.jsonc`，worker 名 `dshop-storefront`） | `npm run build && wrangler deploy --config wrangler.jsonc` + `deploy:dry` | ✅ **已真实部署**    | `https://eshop.eu.cc`       |
| `apps/admin`      | 有（`apps/admin/wrangler.jsonc`，worker 名 `dshop-admin`）          | `npm run build && wrangler deploy --config wrangler.jsonc` + `deploy:dry` | ✅ **已真实部署**    | `https://admin.eshop.eu.cc` |

**三端于 2026-09-26 首次全部真实部署完成**（此前只有 `apps/api` 上线）。按
api → storefront → admin 顺序执行，当前版本 ID：`dshop-api` `33ee7359-0e6f-42c8-98d0-16a8d12cd4da`、
`dshop-storefront` `907abe95-91b3-4752-951d-874c11dd8bcd`、`dshop-admin` `1db2467c-3fa7-41ba-bc9b-f90cf2824781`。

**自定义域**（账号级绑定，非 config 内 `routes`）：`api.eshop.eu.cc` → `dshop-api`、
`eshop.eu.cc` → `dshop-storefront`、`admin.eshop.eu.cc` → `dshop-admin`，三者 `env=production`。

**线上实测结果**（部署后立即用 HTTP 请求验证，非推断）：

| 探测（域名）                                            | 结果                                                                 |
| ------------------------------------------------------- | -------------------------------------------------------------------- |
| `GET eshop.eu.cc/`                                      | 200，`text/html`                                                     |
| `GET eshop.eu.cc/orders/123`（深层链接）                 | 200 —— SPA 回退生效，未 404                                          |
| `GET eshop.eu.cc/assets/index-Dk5876Pq.js`              | 200，`text/javascript`，433 KB                                       |
| `GET eshop.eu.cc/api/v1/agent/orders`（无令牌）          | 401 + `{"code":40101,...}` —— 反代打通，鉴权链路真实生效             |
| `GET admin.eshop.eu.cc/`                                | 200，`text/html`                                                     |
| `GET admin.eshop.eu.cc/orders`（深层链接）               | 200 —— SPA 回退生效                                                  |
| `GET admin.eshop.eu.cc/assets/index-CYYniw6f.js`        | 200，`text/javascript`，1.45 MB                                      |
| `POST admin.eshop.eu.cc/api/v1/admin/login`（空体）      | 400 + `ERR_ADMIN_INVALID_PARAM`，与直连 API 同一路径返回**逐字一致**  |
| `GET api.eshop.eu.cc/health`                            | 200（`environment` 字段见 §13.7：修复前为 `development`）              |
| `GET *.workers.dev`（三个 Worker）                      | **404** —— 自定义域绑定后 `workers_dev` 被禁用，默认域名不再可用       |

> **`routes` 仍未写入 config**：三个 Worker 靠**账号级自定义域**对外服务，`wrangler.jsonc`
> 里没有 `routes` 段。后果是本地无法从配置看出域名归属（`docs/09` §10.2 的平台后台 /
> 商户后台**独立域名分流**仍缺 `merchant.*` 域而未生效——客户端 hostname 分流逻辑已就绪，
> 但需要绑定真实域名才能触发）。
>
> ⚠️ **自定义域绑定的是「顶层环境」，不是 `--env production`**：`api.eshop.eu.cc` 指向
> `dshop-api`（顶层），而 `dshop-api-production`（`env.production`）**并不存在**。
> 因此 **`wrangler.jsonc` 的顶层 `vars` 就是线上变量**——这正是 §13.7 那次事故的成因。

**形态说明**：两个前端都是纯客户端 SPA（React 19 + react-router `BrowserRouter`，无 SSR），
因此各自采用「**薄 Worker + Workers Assets**」形态，而非把静态资源直接当 Worker 上传：

1. `assets.directory: ./dist`、`assets.binding: ASSETS` —— 静态产物由 Workers Assets 托管；
2. `assets.not_found_handling: single-page-application` —— 深层链接刷新回退 `index.html`，
   交给前端路由，避免 404；
3. `assets.run_worker_first: ["/api/*"]` —— **只有** `/api/*` 先经过 Worker，其余请求直接由
   Assets 处理，省一跳；
4. `services: [{ binding: "API", service: "dshop-api" }]` —— Worker 内用 `env.API.fetch(request)`
   同源反代到 API Worker。**必须用 Service Binding 而非公网 `fetch`**（免公网往返与出网计费、
   不依赖 API 对外域名），见 `docs/12-eshop架构对齐审计.md` §12.3.4「必须照抄的硬知识」。

这与前端 `src/api/transport.ts` / `src/api/client.ts` 强制使用相对路径 `/api/v1/*` 的设计
互为闭环：开发期由 Vite 代理转发，生产期由本 Worker 同源反代，前端代码无需感知环境差异。

> 注：`docs/09-认证权限与部署.md` §10 承诺的 `npm run deploy`（= `turbo run deploy`：
> api → storefront → admin）依赖各 workspace 存在 `deploy` script。三个 app 均已具备，
> 且**均可实际部署**。

> ⚠️ 首次部署顺序：必须先部署 `apps/api`（`dshop-api`），否则两个前端的 Service Binding
> 指向的 Worker 尚不存在，`deploy` 会因绑定校验失败。注意 `turbo.json` 目前**只**定义了
> `build` / `typecheck` / `test` / `lint` 四个任务，**没有** `deploy` 任务，故 `turbo run deploy`
> 只是并发跑各 workspace 的 `deploy` script，**不保证** api → storefront → admin 的顺序。
> 首次部署请显式按序执行：
>
> ```bash
> npm run deploy --workspace=@dshop/api
> npm run deploy --workspace=@dshop/storefront
> npm run deploy --workspace=@dshop/admin
> ```

## 13.5 与 eshop 的对齐点与仍存差异

**已对齐**：

- Prettier 代码格式化（配置项与建议命令）；
- 本地 `.dev.vars.example` + 生产 `wrangler secret put` 的 secret 注入纪律；
- 每个 app 具备 `deploy` / `deploy:dry` script，部署命令统一为 wrangler；
- CI 包含类型检查 / 单测 / 静态检查 / 构建 / 契约自检 + 部署 dry-run 门禁。

**仍存差异**（eshop → DShop）：

| 维度     | eshop      | DShop                                                                          | 说明                                                |
| -------- | ---------- | ------------------------------------------------------------------------------ | --------------------------------------------------- |

## 13.7 事故复盘：`ENVIRONMENT` 兼职调试后门导致线上认证绕过

> 本节记录一次**真实发生并被实测复现**的线上事故。它不是假设，而是 2026-09-26 三端首次
> 真实部署、绑定自定义域之后由 `api.eshop.eu.cc/health` 暴露出来的。修复 + 防复发护栏见
> `apps/api/tests/env-flag-discipline.test.ts`。

### 13.7.1 事实链

1. 自定义域 `api.eshop.eu.cc` 绑的是**顶层** Worker `dshop-api`——`dshop-api-production`
   （即 `env.production`）**根本不存在**（`wrangler deployments status --name
   dshop-api-production` 返回 `code 10007`）。故**顶层 `vars` 就是线上变量**。
2. 顶层 `vars.ENVIRONMENT` 当时是 `"development"`。
3. `apps/api/src/routes/shop/auth.ts` 里有一句：
   `if (environment === "development") return "123456";` —— 本意是**本地开发**便利。
4. 于是线上生效：`POST /api/v1/shop/auth/sms-code` 之后，用 `123456` 可以登录**任意** 11 位
   手机号，且**登录即建号**（真实写入 D1）。实测在生产库中创建了用户，事后已全部清理。
5. 同款判断还让认证 Cookie 丢掉 `Secure`（`shop/auth.ts`、`admin/index.ts`、
   `merchant/auth.ts` 各一处），且 `/health` 对外自报 `{"environment":"development"}`。

**为什么测试全绿却仍然中招**：这是**配置语义缺陷**，不是业务逻辑缺陷。所有业务测试里
`ENVIRONMENT` 都是 `"test"`，因此固定码逻辑在测试中从不触发——只有线上那条真实链路才会。

### 13.7.2 修复

| 改动                                        | 位置                                            | 说明                                                                    |
| ------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------- |
| 顶层 `ENVIRONMENT` → `"production"`         | `apps/api/wrangler.jsonc`                       | 顶层即线上；本地 `development` 语义移交 `.dev.vars`                      |
| 新增 `DEMO_FIXED_SMS_CODE` 白名单           | 同上（顶层 + `preview`/`staging`/`production`） | 固定码改由**显式白名单**开启，不再挂在环境标志上                        |
| `generateSmsCode(phone, allowlist)`         | `apps/api/src/routes/shop/auth.ts`              | 签名不再接受 `ENVIRONMENT`，杜绝旧写法复活                              |
| `env.ts` 补声明与警示注释                    | `apps/api/src/env.ts`                           | `ENVIRONMENT` 注明「不得用来开关任何调试后门」                           |
| `.dev.vars.example` 补本地开关              | `apps/api/.dev.vars.example`                    | 本地 `ENVIRONMENT="development"` + `DEMO_FIXED_SMS_CODE="*"`             |
| 结构性护栏测试（10 例）                      | `apps/api/tests/env-flag-discipline.test.ts`    | 三层钉死：配置值、源码签名、调用点                                      |

**为什么用白名单而非布尔开关**：布尔一旦误开，**任意手机号**都能用固定码登录（登录即建号），
爆炸半径 = 全站；白名单把演示能力收敛到指定号码，误配的爆炸半径 = 0。留空即彻底关闭。

**当前取值**：顶层（= 线上）`DEMO_FIXED_SMS_CODE = "13800138000"`（单个演示号）；
`staging` / `production` 命名环境为 `""`（彻底关闭）；`preview` 保留演示号以便 PR 评审进 C 端。

> ⚠️ **遗留影响**：短信通道仍未接入（`docs/09` §9.1），因此**除白名单外的手机号无法登录**——
> 这是有意的：宁可 C 端登录不可用，也不能留一个任意号码可进的认证绕过。接入真实短信通道后，
> 应把顶层白名单一并清空。
